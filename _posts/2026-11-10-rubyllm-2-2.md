[RubyLLM](https://rubyllm.com) 2.2 is out. I released it on stage at SF Ruby.

The talk was about something I hear a lot this year: you don't need frameworks anymore, just let the agent write it. So I tested it. I gave the same coding agent the same app to build with RubyLLM, LangChain, the Vercel AI SDK, and no framework at all. The short version: frameworks matter, but only if agents can use them well. Much of this release came from making sure they can.

2.2 also lets tools ask a person and wait for the answer, keeps a chat alive through a deploy, runs the code a model writes in a sandbox on your own servers, and adds skills, file stores, context budgets, tests without a provider, and four providers. In this post:

## Built for Coding Agents {#coding-agents}

The benchmark: one coding agent, Codex on GPT-6 Astra, builds a chat app in eleven steps. Streaming, persistence, cancel and cost, a second provider to switch to mid-conversation, fallbacks, surviving a restart, approvals, files and sandboxed code, MCP, then Gemini, Azure and Bedrock. After every step a hidden test suite, which the agent never sees, reruns every check on every provider. 198 checks by the end.

Here's the code the agent wrote by hand and still owned at the end. Tests and generated code don't count.

| | Lines |
| --- | ---: |
| **RubyLLM on Rails** | **246** |
| Vercel AI SDK | 748 |
| LangChain | 962 |
| No framework | 1,070 |

And for every provider it added, the lines that speak that provider's own format: zero with RubyLLM, up to 97 without a framework. On Bedrock, the agent signed every request by hand with AWS Signature Version 4 and decoded Amazon's binary event stream frame by frame. With RubyLLM it wrote four lines of configuration, and everything the app already did worked there too.

To check I hadn't just tuned RubyLLM to my own test, I kept a second app out of the loop: a support desk with documents, a sandbox, MCP tools and approvals. With RubyLLM the agent wrote about 420 lines of app code; with no framework, 867.

It wasn't cheaper, though. On the chat app, the latest RubyLLM runs cost about $21 each, and the no-framework runs between $17 and $24. On the support desk, $12.34 against $12.78. The agent still reads a lot, and you pay for every read. I'm working on it. Same bill, half the code.

The surprise was how my first runs went. RubyLLM was installed, its skill was loaded, and the agent still wrote its own price table (with a wrong price), patched the gem to count usage, rebuilt cancellation by hand, and read 280,000 tokens of the gem's source to find things the guides already said. So I spent this cycle making RubyLLM easier for agents to use:

- **The skill ships inside the gem**, so it always matches your version. The new [skill](https://github.com/crmne/skill) gem installs it for Claude Code, Codex or Cursor:

  ```sh
  gem exec skill add "$(bundle show ruby_llm)" --skill rubyllm --agents coding
  ```

  It works like `npx skills`, and it also adds skills to RubyLLM in your Rails app, with a `skills.lock`.

- **The docs are written so an agent finds the answer**: `llms.txt`, and a Markdown version of every page.
- **The API stays small on purpose.** One name per meaning. Every public method is in `api.txt`, and CI fails when it changes without review.
- **The bugs the agents hit are fixed** for everyone: a stale cancel that killed the next reply, one huge tool result that broke the chat, a dead worker that held its chat, no caching on Anthropic and Bedrock, messages lost on refresh.

I'm writing up the whole benchmark, and what I learned optimizing a library for agents, in a separate post.

## Tools Ask a Person {#ask}

A tool can now ask the person running the chat something and carry on with the answer. The call pauses, no process sits waiting, and when they answer, `execute` runs again from the top. Ask first, then act:

```ruby
class BookFlight < RubyLLM::Tool
  description "Books a flight"
  parameter :destination, description: "The city to fly to"

  def execute(destination:)
    seat = ask("Window or aisle?", choices: %w[window aisle]) or return "No seat chosen."
    Flights.book!(destination, seat:)
  end
end
```

An approval is a question too, and MCP servers ask theirs the same way. From any process, you answer with one of three verbs:

```ruby
question = chat.pending_questions.first

question.answer "window"
question.approve remember: true
question.decline "I'll choose at the gate"

chat.complete
```

See [Asking a Person](https://rubyllm.com/tool-execution/#asking-a-person).

## A Chat Survives a Deploy {#deploys}

A persisted chat now runs in one process at a time, so a double-clicked approval never runs a tool twice. If a deploy or a crash cuts off a reply, `Chat.interrupted` finds it, and the chat UI generator writes `ResumeInterruptedChatsJob`, which picks it up as soon as the server boots:

```ruby
Chat.interrupted.find_each { |chat| ChatResponseJob.perform_later(chat.id) }
```

A tool call that had already started never runs again. The model hears it may have partly run, and decides what to do. See [Agents in Background Jobs](https://rubyllm.com/durable-agents/).

## Code in a Sandbox {#code-execution}

A model that can run code calculates exactly, reshapes data, and makes charts, spreadsheets and PDFs. The code was written by a model, so it never runs in your app's process. It runs in a sandbox on your own servers, built on [mxc](https://crmne.github.io/mxc/), my new gem: Microsoft's MXC, from Ruby, improved. It uses the operating system's own isolation, Bubblewrap on Linux and Seatbelt on macOS.

```ruby
class WorkspaceSandbox < MXC::Sandbox
  writable "storage/workspace"
  network false
  timeout 120
  limits cpu_time: 60, memory: 1.gigabyte
end

chat = RubyLLM.chat.with_code_execution(sandbox: WorkspaceSandbox, python: %w[pandas matplotlib])
chat.ask "Plot monthly revenue from this export", with: "revenue.csv"
```

The files the code makes come back as attachments. See [Code Execution](https://rubyllm.com/code-execution/).

## Skills {#skills}

Some tasks need a procedure, not a sentence: how your company formats an invoice, or the script that turns a spreadsheet into slides. Skills keep them in folders, in the open Agent Skills format, and the model loads one only when a task needs it:

```ruby
chat = RubyLLM.chat.with_skills(:invoices).with_code_execution(python: %w[reportlab])
chat.ask "Bill order 1042 to ACME", with: "order-1042.json"
```

With code execution, a skill's scripts run in the sandbox. See [Skills](https://rubyllm.com/skills/).

## File Stores {#file-stores}

A 40-page PDF attached to the first question used to travel with every question after it. With a file store, the model sees it once and then works with it through tools, the way a coding agent does: list, search, read, write and edit.

```ruby
chat = RubyLLM.chat.with_file_store
chat.ask "Which clauses changed?", with: ["contract-v1.pdf", "contract-v2.pdf"]
chat.ask "Quote the new termination clause"
```

Files live in memory, in a folder, or for a persisted chat in Active Storage. See [File Stores](https://rubyllm.com/file-stores/).

## Context Budgets {#context-budgets}

One giant tool result can't break the chat anymore. A context budget cuts results longer than their share and leaves the oldest out of a request that would be too big, while keeping the prompt cache warm:

```ruby
config.context_budget = { per_result: 0.25, per_request: 0.7 }
```

New Rails apps get this line from the install generator. See [Keeping Tool Results in Budget](https://rubyllm.com/chat-request-control/#keeping-tool-results-in-budget).

## Tests Without a Provider {#tests}

Script what the model replies, and test your real chats, agents and pages with no provider and no API key:

```ruby
stub_replies tool_call(:weather, city: "Berlin"), "It is sunny.", cost: 0.01
assert_equal "It is sunny.", SupportAgent.new.ask("Weather?").content
```

See [Testing](https://rubyllm.com/testing/).

## A Generator for Every Building Block {#generators}

Agents, tools, schemas, MCP servers, skills, sandboxes, evaluations and judges each have a generator that puts them in their `app/` folder:

```sh
bin/rails generate ruby_llm:mcp Linear https://mcp.linear.app/mcp
bin/rails generate ruby_llm:skill invoices "Bills an order to a customer as a PDF."
bin/rails generate ruby_llm:sandbox Workspace
```

The generated chat UI now switches models mid-conversation, with a picker on every message, and shows a card for each question a tool asks.

## Four New Providers {#providers}

Moonshot AI (Kimi), MiniMax, Z.ai (GLM) and Meta (Muse) join, for twenty-three built-in providers. Across them, 518 provider features are built in, each checked against the provider's own docs. [The coverage table](https://rubyllm.com/provider-coverage/) lists every one.

There's more, including queued messages, subagents, exclusive tools, three new timeouts and TLS options, in [What's New in 2.2](https://rubyllm.com/whats-new-in-2-2/).

## Where These Features Come From {#chat-with-work}

DHH didn't design a web framework in a room. He built Basecamp and pulled out what kept working. RubyLLM comes from [Chat with Work](https://chatwithwork.com) the same way: everything new in 2.2 earned its place there first.

Chat with Work makes AI bots that work for you. A bot starts on an event or a time and works across your tools, changes ask first unless you let them run, and everything that needs you lands in one list. Every one of those chats is rows in my own database. Asking a person, surviving deploys, sandboxed code and file stores all came from needing them there.

## Upgrading {#upgrading}

```sh
bundle update ruby_llm
bin/rails generate ruby_llm:upgrade
bin/rails db:migrate
```

A few methods changed. `pending_questions` replaces the separate lists of approvals and inputs, and `decline` replaces `deny`. [The upgrade guide](https://rubyllm.com/upgrading/) gives each one's replacement. Coming from 1.16? Upgrade one release at a time.

Try it, and tell me what you find.
