[RubyLLM 2.0](/rubyllm-2-0/) came out three weeks ago. I called it the biggest release since 1.0.

2.1 is out today (I just released it on stage at Deccan Queen on Rails in Pune), and it brings an MCP client, typed judgments, evaluations, tool progress, OpenTelemetry tracing, a nineteenth provider, and a long list of things that got faster without you touching your code.

```ruby
class Linear < RubyLLM::MCP
  url "https://mcp.linear.app/mcp"
  inputs :user
  oauth owner: :user

  only :list_issues, :get_issue, :create_issue
  requires_approval :create_issue
end

chat = RubyLLM.chat.with_mcp(Linear.new(user: current_user))
chat.ask "What's blocking the release?"
```

That's a Linear MCP server, with per-user OAuth, three tools out of however many Linear ships, and a human in the loop before anything gets created. Here's the rest.

## An MCP Client You Configure Like a Tool

Yes, I'm the person who wrote that your agent's [context window is not a junk drawer](/your-agents-context-window-is-not-a-junk-drawer/), with MCP as the biggest offender. I still think so. That's exactly why the client looks like this.

A server hands your model every tool it has, written by someone else for every possible client. In RubyLLM you describe the server in a class, and the class decides what the model sees:

```ruby
class GitHub < RubyLLM::MCP
  url "https://api.githubcopilot.com/mcp/"
  bearer_token ENV.fetch("GITHUB_TOKEN")

  only :search_issues, :get_issue
  tool :search_issues, as: :search_ruby_llm_issues,
       description: "Search RubyLLM's issues. Use GitHub search syntax.",
       fixed_arguments: { owner: "crmne", repo: "ruby_llm" }
end
```

`only` keeps the tools you need. `tool` renames them, rewrites their descriptions, and takes arguments away from the model so it can't search anywhere you didn't intend. `wrap:` passes results through your own method before the model reads them, and a regular `RubyLLM::Tool` can build one sharp tool out of a server's low-level primitives.

Every server tool is also a Ruby method, so you can poke at a server from the console before giving it to a model:

```ruby
docs = RubyLLM.mcp(url: "https://learn.microsoft.com/api/mcp")
docs.tools
docs.microsoft_docs_search(query: "Azure Blob Storage").text
```

The rest is the protocol done properly. Resources work as attachments and prompts work with `ask`. When a server asks the user for input mid-call, the chat pauses the same way it pauses for a tool approval, and in Rails that pause survives a restart. OAuth follows the MCP authorization spec with credentials encrypted in your database, background jobs can connect as the app itself, and servers that require DPoP get key-bound tokens without you configuring anything. Servers that change their tools are picked up on the next turn, and `listen` lets you react to changes as they happen. MCP Apps and Tasks are supported as extensions.

If you used the community `ruby_llm-mcp` gem, remove it before updating: it defines the same `RubyLLM::MCP` constant.

The full story is in [the MCP post](/rubyllm-2-1-mcp/) and the [MCP guide](https://rubyllm.com/mcp/).

## Know Whether Your Agent Is Right

Most of what we ask models in production isn't conversation. It's questions about our own data: is this urgent, which team owns it, how frustrated is this customer. 2.1 gives those questions a shape:

```ruby
class TicketTriage < RubyLLM::Judge
  probability :urgent, "Does this need attention today?"

  choice :department, "Which team should handle this?" do
    billing "Payments and refunds"
    technical "Bugs and integrations"
    other "Everything else"
  end
end

judgment = TicketTriage.judge("Please refund the duplicate charge today.")
judgment.urgent.probability
judgment.department.choice
```

You get probabilities, choices with full distributions, and scores, so your code decides what "urgent enough" means instead of parsing "Yes." out of a sentence. Judges run on TypeSafe's Jev models, through TypeSafe as a new provider or any Jev-compatible local server, and on OpenAI's `gpt-6-luna` through OpenAI Decisions, which Kieran Klaassen added (#1008), images included.

Then there's the question every agent builder eventually asks at 2 a.m.: did that prompt change make things better or worse? Evaluations answer it with a class and a YAML file:

```ruby
# app/evals/support_evaluation.rb
class SupportEvaluation < RubyLLM::Evaluation
  def perform(input)
    SupportAgent.new.ask(input)
  end
end
```

```yaml
# app/evals/support_evaluation.yml
cases:
  - name: unopened_return
    inputs: Can I return an unopened item after 14 days?
    expected_output: Yes, unopened items can be returned within 30 days.
```

```sh
bin/rails "ruby_llm:eval[SupportEvaluation]"
```

A model checks each answer against the reference and accepts different wording with the same meaning. You can declare your own criteria, grade with an Agent or a Judge, assert on tool calls in plain Ruby, and run the same cases from RSpec or Minitest. The report shows every verdict with its reason, and what the run cost.

More in [the judgments and evaluations post](/rubyllm-2-1-judgments-and-evaluations/), and the [Judgments](https://rubyllm.com/judgments/) and [Evaluations](https://rubyllm.com/evaluations/) guides.

## Faster Without Changing Your Code

I spent a good part of this release measuring RubyLLM's own overhead with the providers taken out of the picture, and fixing what showed up. A few of the results, 2.0 against 2.1 on the same machine:

| Workload | 2.0 | 2.1 |
| --- | --- | --- |
| Stream a 2 MB event that arrives in 16 KB pieces | 116 ms | 2.0 ms |
| Stream 500 Perplexity chunks that each cite 20 sources | 137 ms | 17 ms |
| Memory kept by a streamed 40-turn chat with a 256 KB image | 28 MB | 0.48 MB |
| Eight threads loading the model registry at once | 273 ms | 32 ms |
| The same persisted chat without `automatic_scope_inversing` | 58 queries | 8 queries |

Calls also share HTTP connections now. Pick an adapter that keeps them open and every call after the first skips the TCP and TLS handshake:

```ruby
RubyLLM.configure do |config|
  config.faraday_adapter = :net_http_persistent # or :async_http inside an Async reactor
end
```

There's a [whole post on what got faster and why](/rubyllm-2-1-faster/), including the one that was quietly quadratic. The benchmarks need no API keys, so you can check my numbers on your own machine with `bundle exec rake "benchmark:compare[v2.0.0]"`.

## Tools That Say What They're Doing

A tool that downloads a file and reads forty scanned pages takes a while. Until now your user stared at a spinner. Now the tool can tell them what's happening:

```ruby
class ReadReport < RubyLLM::Tool
  def execute(url:)
    progress "Downloading #{File.basename(url)}"
    pages = Scanner.pages(url)
    pages.each_with_index.map do |page, index|
      progress "Reading page #{index + 1} of #{pages.size}", value: index + 1, total: pages.size
      page.text
    end.join("\n")
  end
end

chat.with_tools(ReadReport).after_tool_progress do |tool_call, progress|
  puts "#{tool_call.name}: #{progress.message}"
end
```

MCP server tools report through the same callback, so your UI doesn't care where a tool lives. It works with concurrent tool execution, on agents, and on Rails chat records. See [Reporting Progress](https://rubyllm.com/tool-execution/#reporting-progress).

## OpenTelemetry in One Line

1.16 gave you Rails-style instrumentation events. 2.1 turns them into traces:

```ruby
RubyLLM::OpenTelemetry.enable
```

Add the `opentelemetry-api` gem, and model calls, tool runs, and workflows become spans that follow the OpenTelemetry GenAI conventions, sent through whatever SDK and exporter your app already configures. They carry models, token counts, and finish reasons, never prompts or responses. Your tracing vendor doesn't need to read your users' conversations to tell you a call was slow. See the [OpenTelemetry guide](https://rubyllm.com/opentelemetry/).

## And Also

- **Hetzner** is provider number nineteen (TypeSafe was eighteen). Its experimental Inference API serves open-weight models from Hetzner's data centers: `RubyLLM.chat(model: "Qwen3.8-27B", provider: :hetzner)`.
- **Per-tenant agents.** A `context` block without arguments now runs when the chat is built, with the agent's inputs available, so each workspace can bring its own API key or endpoint. Thanks to mikemikimike (#903). See [Configuration Contexts](https://rubyllm.com/agents/#configuration-contexts).
- **A secondary database.** RubyLLM's supporting records can live on the same secondary database as your chats and messages. See [Advanced Rails Configuration](https://rubyllm.com/rails-advanced-config/).
- **Usage beyond chats.** In Rails, `RubyLLM.transcribe`, `RubyLLM.embed`, and the other one-shot operations write to the usage ledger too. Attribute them with `owner: current_user` or wrap a job in `RubyLLM.with_usage_owner(user) { ... }`.
- **`error.request_shape`.** When a provider rejects a conversation with nothing more helpful than "Request contains an invalid argument," `request_shape` lists every turn's parts and their sizes (never their contents) and flags the problems providers are known to refuse. It beats bisecting a transcript by hand.
- **Perplexity chat runs on the Agent API**, since Sonar retires. Chats that name a Sonar model keep working: they run the preset Perplexity recommends and log a deprecation warning.
- **Upgrades, one release at a time.** From 2.1 on, each release ships the upgrade from the release before it. In 2.1, `bin/rails generate ruby_llm:upgrade` adds the tables and columns the MCP client, provider file reuse, and the wider usage ledger need. Coming from 1.x? Upgrade to 2.0 first.
- **Ruby 3.1 is gone**, since it reached end of life. RubyLLM now needs Ruby 3.2 or later.
- **JSON 3 is allowed**, thanks to Filipe Kalicki (#968). On Rails before 8.1.4, keep `gem "json", "< 3"` in your Gemfile.

## Get It

```ruby
gem "ruby_llm", "~> 2.1.0"
```

```bash
bundle update ruby_llm
bin/rails generate ruby_llm:upgrade
bin/rails db:migrate
```

Most 2.0 apps need no code changes. The few that do (Perplexity chats, `raw.env.request_body`, rescuing provider limits, renamed tool use counters, blocked Gemini transcriptions) are listed in the [upgrade guide](https://rubyllm.com/upgrading/). Everything new is in [What's New in 2.1](https://rubyllm.com/whats-new-in-2-1/).

I can't promise a release like this every three weeks. But most of 2.1 was built on 2.0's foundations rather than around them, which is the whole point of having done 2.0.
