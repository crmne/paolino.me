RubyLLM 2.0 came out on September 18. This is the announcement post, two and a half weeks late, because I've been too busy shipping to write about shipping.

It's the biggest release since 1.0. Here's the short version:

```ruby
class RefundOrder < RubyLLM::Tool
  description "Refunds an order"
  parameter :order_id, description: "ID of the order to refund"
  requires_approval

  def execute(order_id:, tool_call: nil)
    Refunds.issue(order_id:, idempotency_key: tool_call.id)
  end
end

class SupportAgent < RubyLLM::Agent
  chat_model Chat
  tools RefundOrder
end

chat = SupportAgent.create!
chat.ask "I was charged twice for order 42."
chat.awaiting_approval? # => true. Nothing has been refunded.
```

The agent asked to refund an order, and RubyLLM stopped. The tool call is saved in your database. A person can approve it tomorrow, from a different process, after two deploys, and the agent picks up exactly where it left off.

That's one piece. 2.0 also generates video and speech, reads scanned documents, reranks search results, runs provider-hosted tools with typed citations, accounts for every provider attempt (including the ones that failed), and works across seventeen providers. Chat is still the heart of RubyLLM. It's no longer most of it.

Here's the tour.

## Agents That Wait for a Human

Some actions shouldn't happen just because a model asked. Refunds, deletions, emails to customers. Declare `requires_approval` on the tool, and the loop parks instead of running it.

In Rails, the pending call lives on a tool-call record, so the approval can come from anywhere:

```ruby
class ApprovalsController < ApplicationController
  def create
    chat = Chat.find(params[:chat_id])
    chat.approve(params[:tool_call_id]) # or chat.deny(...)
    CompleteJob.perform_later(chat.id)
  end
end

class CompleteJob < ApplicationJob
  def perform(chat_id)
    SupportAgent.find(chat_id).complete
  end
end
```

`SupportAgent.find` reloads the transcript and reapplies the agent's tools and configuration. Tool calls that already have saved results are skipped. Denials go back to the model as a tool result, so it can apologize, ask a follow-up, or try something else.

`chat.pending_approvals` gives you the calls to render in your UI. That's the whole API. No workflow engine, no state machine to serialize. The transcript is the state.

One rule comes with it: a process can die after a tool's side effect succeeds and before its result is saved, so tools that write should be idempotent. That's why the refund above passes `tool_call.id` as an idempotency key.

The [tool approval guide](https://rubyllm.com/tool-execution/#requiring-approval) and [durable agents guide](https://rubyllm.com/durable-agents/) cover the full flow, including ActiveJob Continuations for surviving deploys mid-run.

## The Loop, One Step at a Time

`ask` still runs the whole agentic loop for you. When you want control, 2.0 breaks it into verbs:

```ruby
chat = RubyLLM.chat.with_tools(SearchDocs).ask_later("How do I configure webhooks?")
chat.step until chat.complete? || chat.awaiting_approval?
```

`ask_later` stages a message. `generate` makes one model call. `run_tools` runs pending tools. `step` picks the next move. `complete` keeps going until there's an answer or a decision to make. `cancel` stops a run from another thread, or, in Rails, from another process through the database.

Iteration budgets, one step per job, handoffs between agents: they're all a few lines of Ruby now. I wrote about this in detail in [The Agentic Loop, Exposed](/rubyllm-2-0-agentic-loop/).

## New Verbs

1.x could chat, embed, paint, transcribe, and moderate. 2.0 adds a verb for most of what's left:

```ruby
RubyLLM.animate("A red panda typing Ruby code").save("panda.mp4")
RubyLLM.speak("Welcome to the Ruby study group.").save("welcome.mp3")
RubyLLM.ocr("scanned-contract.pdf").markdown
RubyLLM.rerank("How do I reset my password?", documents, model: "rerank-v3.5")
RubyLLM.embed("A red panda", with: "panda.jpg", model: "gemini-embedding-2")
RubyLLM.tokenize("Hello, Ruby!", model: "grok-4.3").ids
```

They work in scripts, services, and jobs, without a chat. Results are typed, media saves with `save`, and long-running jobs like video have `_later` versions you can poll from another process. Transcription gained shared controls for speaker labels and timestamps too.

Each one has a guide: [video](https://rubyllm.com/video-generation/), [speech](https://rubyllm.com/text-to-speech/), [OCR](https://rubyllm.com/ocr/), [reranking](https://rubyllm.com/rerank/), [embeddings](https://rubyllm.com/embeddings/), and [tokenization](https://rubyllm.com/tokenization/).

## Provider Tools and Citations

Providers now run tools on their own infrastructure: web search, code execution, file search, remote MCP servers. 2.0 gives them one API, and the answers come back with sources you can render:

```ruby
chat = RubyLLM.chat(model: "claude-sonnet-5").with_provider_tools(:web_search)
response = chat.ask "What changed in the latest Ruby release?"

response.citations.each { |citation| puts "#{citation.title}: #{citation.url}" }
```

Mix them with your own Ruby tools on the same chat. Citations are typed values whether they come from web search, a PDF you attached with `with_citations`, or your own retrieval tool. They survive streaming and Rails persistence.

See [Provider Tools](https://rubyllm.com/provider-tools/) and [Citations](https://rubyllm.com/citations/).

## A Cost Ledger That Counts Every Attempt

Your chat history is not a bill. A retry that failed, a fallback model that took over, a stream the user cancelled halfway: they all cost tokens, and none of them leave a tidy assistant message behind.

2.0 records usage per provider attempt. The API stays small:

```ruby
chat = RubyLLM.chat.with_fallbacks("claude-sonnet-5")
response = chat.ask "Explain Ruby fibers in one paragraph."

response.tokens.input
response.cost.total
chat.cost.total # every attempt, including the ones that failed
```

When usage or pricing is unknown, the total is `nil`, not zero. A request you can't price shouldn't look free. Provider-reported charges win over estimates, and in Rails the cost is frozen when the attempt finishes, so a price change next month doesn't rewrite last month.

The [Tokens and Costs guide](https://rubyllm.com/cost-and-usage-tracking/) explains exactly what each total includes. [Model fallbacks](https://rubyllm.com/error-handling/#model-fallbacks) have their own section.

## Seventeen Providers, Much More of Each

Cohere, Ollama Cloud, ElevenLabs, and Deepgram join the list, bringing the total to seventeen.

The bigger change is depth. I audited forty shared features across all seventeen providers, comparing 1.16 with 2.0. Built-in support went from 170 provider-feature pairs to 395, out of the 405 those providers offer. That's not 395 different features, and it's not every endpoint every provider has. It is a lot more of each provider's API reachable from the same Ruby code.

The [coverage matrix](https://rubyllm.com/provider-coverage/) shows every cell, with sources and the gaps that remain.

Under the hood, providers and protocols are now separate. OpenAI defaults to the Responses API, Vertex AI and Bedrock route each model to the API it actually speaks, and a new provider can be a single small file. If yours is missing, generate a gem for it:

```bash
ruby_llm provider-gem Acme --api-base https://api.acme.ai/v1
```

I covered the design in [Providers, Protocols, and Provider Gems](/rubyllm-2-0-providers-and-protocols/).

## The Rest of the Box

There's a lot more, and most of it deserves its own post. Briefly:

- **Batches.** Stage chats with `ask_later`, submit them with `RubyLLM.batch`, collect the answers later from another process at the provider's batch rates. [Guide](https://rubyllm.com/batches/).
- **Prompt caching.** `with_caching` and `cache_until_here` work the same way across providers, and `RubyLLM.cache` manages Gemini and Vertex AI cache resources. [Guide](https://rubyllm.com/prompt-caching/).
- **Thinking.** `with_thinking` uses the model's defaults, or pass `effort:` or `budget:`. Read it back through `response.thinking`. [Guide](https://rubyllm.com/thinking/).
- **Files.** `RubyLLM.upload` once, reuse everywhere. Large attachments upload automatically, and tools can return files. [Guide](https://rubyllm.com/files/).
- **Request control.** Replace the transcript with `messages=`, compact long conversations with `with_compaction`, inspect the payload with `render`, edit it with `before_request`. [Guide](https://rubyllm.com/chat-request-control/).
- **Prompt templates.** ERB files in `app/prompts`, rendered anywhere with `RubyLLM.render_prompt`. Named agents find theirs by convention. [Guide](https://rubyllm.com/prompt-rendering/).
- **Workflows.** `RubyLLM.workflow` names a task and its steps in your instrumentation, while the orchestration stays plain Ruby. [Guide](https://rubyllm.com/instrumentation/).

## Less Bookkeeping in Your Rails App

In 1.x, your app owned `Model` and `ToolCall` classes that were really RubyLLM's business. In 2.0, your app owns `Chat` and `Message`, and RubyLLM owns its registry, tool calls, usage, and batches under a `ruby_llm_` prefix. Every feature above that needed new columns got them without asking you to maintain another model.

The API got a consistency pass too. One name per concept: `tokens`, `provider_options`, `before_` and `after_` callbacks. Value setters take `nil` to reset. Feature switches like `with_thinking` take `false` to turn off. Small things, but you stop having to look them up.

## Teach Your Coding Assistant

The gem ships a RubyLLM skill for coding assistants, maintained alongside the code and guides. Install the copy that matches your bundle:

```bash
npx skills add "$(bundle show ruby_llm)" --skill rubyllm
```

Your assistant stops writing 1.x method names from its training data and stops rebuilding things RubyLLM already does. [Setup details](https://rubyllm.com/ai-coding-assistants/).
