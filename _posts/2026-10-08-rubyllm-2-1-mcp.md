```ruby
class Linear < RubyLLM::MCP
  url "https://mcp.linear.app/mcp"
  inputs :user
  oauth owner: :user

  only :list_issues, :get_issue, :create_issue
  requires_approval :create_issue
end

chat = RubyLLM.chat.with_mcp(Linear.new(user: current_user))
chat.ask "What's blocking the release?"
```

That's an MCP server in [RubyLLM](https://rubyllm.com) 2.1, out today. Each user connects their own Linear account. The model sees three tools out of everything Linear offers, and it can't file an issue until a person says yes.

Yes, I'm aware. In April I wrote that your agent's [context window is not a junk drawer](/your-agents-context-window-is-not-a-junk-drawer/), called MCP the biggest offender, and signed off with "Use MCP to prototype. Then replace it with crafted tools you actually control."

I stand by every word. That's why the client looks like this.

## The Problem Was Never the Protocol

The trouble with MCP is what clients do with it. Plug a server in and the model gets every tool on it, with descriptions you didn't write, schemas you didn't read, and a tool count that grows every time the vendor ships. The server decides what goes into your context. You find out later, if ever.

So RubyLLM treats a server the way it treats everything else that touches the model: as a Ruby class you own. It lives in your repo, it shows up in code review, and it says exactly what the model gets. The server offers. You decide.

Small detail I like: when a server sends instructions, `docs.instructions` lets you read them. They don't go into your system prompt unless you put them there.

## Poke It From the Console First

Prototyping is where MCP shines, so that part should take one line:

```ruby
>> docs = RubyLLM.mcp(url: "https://learn.microsoft.com/api/mcp")
>> docs.tools
=> [#<RubyLLM::MCP::Tool name: "microsoft_docs_search", read_only: true>, ...]
>> docs.microsoft_docs_search(query: "Azure Blob Storage").text
=> "..."
```

Every tool on the server is a Ruby method, the way Active Record turns columns into attributes. You can read what a server offers, call it by hand, and see what comes back before a single token of it goes anywhere near a model. `docs.call("tool-name", **args)` covers tools whose names aren't valid Ruby.

That's the prototyping half of my advice, and it's now the fastest way I know to evaluate an MCP server.

## Then Craft It

The other half was "replace it with crafted tools you actually control." In 2.1, you don't have to throw the prototype away. You shape it in the class:

```ruby
class GitHub < RubyLLM::MCP
  url "https://api.githubcopilot.com/mcp/"
  bearer_token ENV.fetch("GITHUB_TOKEN")

  only :search_issues, :get_issue
  tool :search_issues, as: :search_our_issues,
       description: "Search RubyLLM's issues. Use GitHub search syntax.",
       fixed_arguments: { owner: "crmne", repo: "ruby_llm" },
       wrap: :trim

  private

  def trim(result, **)
    result.text[0, 4_000] # the model needs a list, not the whole of GitHub
  end
end
```

* `only` keeps the tools you name and drops the rest. `except` does the opposite.
* `tool :name, as:, description:` renames a tool and rewrites what the model reads about it. Your words, your tokens.
* `fixed_arguments:` takes arguments away from the model and always sends your values. The model sees `search_our_issues` without `owner` or `repo`, so it can't wander off to someone else's repository. Values can be lambdas when they depend on inputs.
* `wrap:` runs the server's result through your own method before the model sees it.
* `prefix :github` keeps two servers that both have a `search` tool from colliding in one chat.

When the server's primitives are too low-level, build a better tool out of them with a regular `RubyLLM::Tool`. Add it with `tool SearchAndRead`, and if its `initialize` takes an argument, it receives the server, so it can call `@dropbox.search(...)` and `@dropbox.get_file_content(...)` like any other Ruby object. The server's tools stay callable as methods even when `only` hides them from the model.

One more thing I care about: every tool name you declare must exist on the server. If the vendor renames or removes one, RubyLLM raises `RubyLLM::ConfigurationError` when the tools load, instead of quietly changing what your model sees.

## Approvals and Questions That Survive a Deploy

Some tools shouldn't run without a person saying yes. `requires_approval` uses the same flow as Ruby tools since 2.0:

```ruby
requires_approval :create_issue, :merge_pull_request
requires_approval if: :destructive?
```

`destructive?` is the server's own hint about the tool, so trust it as far as you trust the server.

Servers can also stop in the middle of a call and ask the user something: which environment, or "visit this page to connect your account." A callback can answer with `before_input_request`. Otherwise the chat pauses, exactly like it pauses for an approval:

```ruby
class Deploys < RubyLLM::MCP
  url "https://deploys.example.com/mcp"
  inputs :user
  oauth owner: :user
  requires_approval if: :destructive?
end

class ReleaseAgent < RubyLLM::Agent
  chat_model Chat
  instructions "You ship releases."
  mcp { Deploys.new(user: chat.user) }
end

chat = ReleaseAgent.create!(user: current_user)
chat.ask "Deploy the release branch"
chat.awaiting_input?                  # => true
chat.pending_inputs.first.message     # => "Which environment?"
```

In Rails, the request persists on the tool call. A controller records the answer, and a job picks the call back up, after a restart or a deploy if that's what happened in between:

```ruby
class DeployInputsController < ApplicationController
  def create
    chat = current_user.chats.find(params[:chat_id])
    chat.answer(chat.pending_inputs.first, environment: params[:environment])
    ResumeReleaseJob.perform_later(chat.id)
    head :no_content
  end
end

class ResumeReleaseJob < ApplicationJob
  def perform(chat_id)
    ReleaseAgent.find(chat_id).complete
  end
end
```

`chat.decline(request)` refuses, and `chat.waiting?` tells you the chat is parked on approvals, answers, or tasks. Servers never ask for passwords through forms: those go through URL requests, so they never pass through your app.

## Servers Change Under You

Tools appear when a user connects another account. A document a server serves gets edited. When a server says its tools changed, the next turn of the chat sees the new list. To hear about changes as they happen, call `listen` and react with `after_change`:

```ruby
class Handbook < RubyLLM::MCP
  url "https://handbook.example.com/mcp"
  after_change { |change| ReindexPolicyJob.perform_later(change.uri) if change.is_a?(RubyLLM::MCP::Resource) }
end

Handbook.new.listen(resources: ["handbook://policies"])
```

`after_change` receives `:tools`, `:prompts`, or `:resources` when a list changes, the resource whose content changed, or a task whose status changed. The listener runs in its own thread, reconnects with backoff when the connection drops, and once it's back, treats everything as changed so nothing slips through the gap. Give it a process of its own (one Procfile line with `bin/rails runner`). In Rails, its callbacks run inside the executor, like a job.

Resources and prompts come along too. A resource is an attachment, so `chat.ask "Summarize this", with: files.resource("file:///project/README.md")` just works, and `chat.ask github.prompt(:code_review, code: diff)` asks with a server's prompt.

## The Auth Nobody Wants to Write

This is where most of the 2.1 work went, and where I hope you never have to look.

OAuth follows the MCP authorization spec: discovery, dynamic registration or client ID metadata documents, PKCE. `authorization_url` sends the user off, `authorize(params)` finishes in your callback, and from then on tokens refresh by themselves. In Rails they live in an encrypted `ruby_llm_mcp_credentials` table, and refreshes take turns across processes so a rotating refresh token never gets used twice. Background jobs can connect as your app with `grant: :client_credentials`, sign assertions with a `private_key:`, or present a Kubernetes or SPIFFE token through the JWT bearer grant. Companies can authorize their people through their identity provider with `identity_provider:`, so an Okta user skips the consent screens and the company decides who reaches which server. Servers that require DPoP get tokens bound to a key RubyLLM creates and keeps, with nothing for you to configure.

The client speaks the 2026-07-28 revision of the protocol and falls back to older servers back to 2024-11-05. The official MCP conformance suite runs in CI on every change. Plain HTTP only to localhost, no redirects followed, and no headers in request logs, because tokens don't belong in logs.

## Apps and Tasks

Two protocol extensions are built in, and you opt into each with one line:

```ruby
class Reports < RubyLLM::MCP
  url "https://reports.example.com/mcp"
  extension :apps
  extension :tasks
end
```

With **MCP Apps**, a tool comes with a UI, like a chart or a form, that your app renders next to the result in a sandboxed iframe. The tool result keeps the server's full result as `mcp_result`, persisted in Rails, so the UI renders the same after a reload. Tools meant only for the UI never reach the model, even if you pass them to `with_tools`.

With **Tasks**, a server runs a long call in the background and the chat doesn't wait for it. The tool call pauses the same way approvals and input requests do, `chat.awaiting_tasks?` says so, and a job calls `complete` later to check in. No worker sits there holding a connection while a quarterly report renders.

## Two Kinds of MCP

RubyLLM 2.0 already let providers call MCP servers for you with `with_provider_tools(mcp: ...)`. That still works, and it's fine when the provider's hosted connector is what you want. The 2.1 client is the other kind: the calls happen in your process, so everything above applies. Your names, your descriptions, your approvals, your logs.

Before this, [ruby_llm-mcp](https://github.com/patvice/ruby_llm-mcp) by @patvice carried MCP for RubyLLM users for a long time. Thank you.

## Use It

```ruby
gem "ruby_llm", "~> 2.1.0"
```

Rails apps on 2.0 run the upgrade generator, which adds the credentials table and the columns that keep paused calls and app results:

```bash
bin/rails generate ruby_llm:upgrade
bin/rails db:encryption:init   # only if your app has no encryption keys yet
bin/rails db:migrate
```

The [MCP Client guide](https://rubyllm.com/mcp/) covers everything here and more: stdio servers, custom transports, resource templates, progress and logs, cancellation, and connecting to servers your users add at runtime.

My advice hasn't changed. Prototype with MCP, then craft the tools your agent actually needs. The difference is that now both steps happen in the same Ruby class.
